# KBot - Telegram Бот

KBot - це CLI-додаток, створений за допомогою Cobra, який запускає Telegram-бота, реалізованого на бібліотеці Telebot. Бот надає набір команд для взаємодії з користувачами.

## Опис

Цей застосунок є інструментом для запуску Telegram-бота `KBot`. Він використовує бібліотеку Cobra для управління командами командного рядка та Telebot для взаємодії з Telegram API.

### Адреса бота: t.me/tirthika_bot

## Можливості

* **Інтерфейс командного рядка**: Керування ботом через команди CLI.
* **Telegram Бот**:
    * Відповідає на команду `/start` вітальним повідомленням.
    * Відповідає на команду `/hello` персоналізованим привітанням.
    * Надає список доступних команд за допомогою `/help`.
    * Показує версію програми за командою `/version`.
    * Відповідає "pong" на команду `/ping`.
    * Реагує на будь-який інший текст повідомленням-заглушкою.

## Передумови

* Встановлений [Go](https://golang.org/dl/) (версія 1.16+ рекомендується).
* Токен Telegram Бота (отриманий від [@BotFather](https://t.me/BotFather)).

## Використання

Для запуску бота виконайте наступну команду:

```bash
go run main.go kbot
# або якщо ви скомпілювали проект:
# ./<назва_скомпільованого_файлу> kbot
```

Після запуску, консоль виведе повідомлення про старт бота, і він почне обробляти команди в Telegram.

Приклад:
```bash
go run main.go kbot
# Або, якщо ваш головний файл називається інакше, наприклад app.go:
# go run app.go kbot
```
kbot vX.Y.Z started
```
(де `vX.Y.Z` - це значення змінної `appVersion`)

## Доступні команди бота в Telegram

Після запуску бота, ви можете взаємодіяти з ним у Telegram за допомогою наступних команд:

* `/start` - Почати взаємодію з ботом.
* `/help` - Ця команда виводить перелік команд, які приймає Kbot.
* `/version` - Показує версію програми Kbot.
* `/hello` - Поверне вітальне значення.
* `/ping` - Відповідає "pong".

## 1. Передумови

## 2. Огляд Makefile

`Makefile` автоматизує процес збірки, тестування та керування Docker-образами для проекту `kbot`.

### Основні змінні

* `WITHDOCKER`: Якщо встановлено в `true` (наприклад, `make WITHDOCKER=true linux/amd64`), після збірки бінарного файлу буде також зібрано Docker-образ для відповідної платформи. За замовчуванням: `false`.
* `REPO`: Префікс репозиторію для Docker-образів (наприклад, `github.dev/devops101-prom`).
* `VERSION`: Автоматично визначається на основі тегів Git та хешу коміту (наприклад, `v1.0.0-g1a2b3c4`).
* `APP_NAME`: Назва програми (`kbot`).
* `OUTPUT_DIR`: Директорія для збереження скомпільованих бінарних файлів (`./bin`).
* `TARGET_PLATFORMS`: Список підтримуваних комбінацій ОС/архітектура для збірки.
* `IMG-RM`: Якщо встановлено в `true` при виконанні `make clean` (наприклад, `make clean IMG-RM=true`), будуть видалені локальні Docker-образи, що відповідають `$(REPO)/$(APP_NAME):$(VERSION)*`.

### Цілі Makefile

* **`all` (ціль за замовчуванням)**:
    * Відображає список дозволених комбінацій ОС/архітектура (`TARGET_PLATFORMS`).
    * Пропонує запустити неіснуючу ціль `~build-all~`. Для фактичної збірки всіх платформ використовуйте індивідуальні цілі або створіть нову ціль `build-all`, яка б викликала збірку для кожної платформи з `$(TARGET_PLATFORMS)`.

* **`<os>/<arch>` (наприклад, `make linux/amd64`, `make windows/arm64`)**:
    * Збирає бінарний файл `kbot` для вказаної операційної системи (`os`) та архітектури (`arch`).
    * Залежить від `$(OUTPUT_DIR)` (створює директорію, якщо потрібно) та `install-dep`.
    * Бінарний файл зберігається як `$(OUTPUT_DIR)/$(APP_NAME)-<os>-<arch>` (або `...exe` для Windows).
    * **Збірка Docker-образу**: Якщо `WITHDOCKER=true`, також буде зібрано Docker-образ за допомогою `Dockerfile.mk` (див. [Важливі примітки](#5-важливі-примітки)) для цієї платформи. Тег образу буде `$(REPO)/$(APP_NAME):$(VERSION).<os>-<arch>`.

* **`install-dep`**:
    * Виконує `go get` для завантаження/оновлення залежностей проекту.

* **Аліаси для зручності**:
    * `make linux`: Збирає для `linux/amd64`.
    * `make arm`: Збирає для `linux/arm64`.
    * `make windows`: Збирає для `windows/amd64`.
    * `make macos`: Збирає для `darwin/amd64`.
    * *Примітка: Makefile містить також цілі типу `linux-amd64`, `darwin-arm64` тощо, які залежать від неіснуючих цілей `build-<os>-<arch>`. Рекомендується використовувати формат `<os>/<arch>`.*

* **`test`**:
    * Запускає тести Go (`go test -v ./...`).

* **`clean`**:
    * Видаляє директорію з артефактами збірки (`$(OUTPUT_DIR)`).
    * Якщо `IMG-RM=true`, також видаляє локальні Docker-образи, що відповідають поточному `REPO`, `APP_NAME` та `VERSION`.

* **`docker-push`**:
    * Призначена для публікації Docker-образу в регістр.
    * **Увага**: У поточному вигляді ця ціль (`docker push $(APP_NAME):$(VERSION).$(1)-$(2)`) не буде працювати коректно, оскільки змінні `$(1)` та `$(2)` не визначені в її контексті. Цю ціль слід викликати після успішної збірки конкретного образу або модифікувати для ітерації по зібраних образах. Наприклад, після `make WITHDOCKER=true linux/amd64`, ви можете вручну виконати `docker push $(REPO)/$(APP_NAME):$(VERSION).linux-amd64`.

## 3. Огляд Dockerfile (`Dockerfile.multiarch.runnable`)

Цей `Dockerfile` (рекомендована назва `Dockerfile.multiarch.runnable`, хоча Makefile посилається на `Dockerfile.mk`) призначений для створення багатоархітектурних, готових до запуску Docker-образів для `kbot`.

### Призначення

* Створення оптимізованих Docker-образів для різних платформ (Linux, Windows).
* Використання `Makefile` для процесу компіляції всередині Docker.
* Встановлення `ENTRYPOINT` для легкого запуску бота.

### Етапи збірки

1.  **`builder` етап**:
    * Базується на `golang:1.22-alpine`.
    * Копіює вихідний код та `Makefile`.
    * Завантажує Go-модулі.
    * Виконує `make "${TARGETOS}/${TARGETARCH}"` для компіляції бінарного файлу `kbot`. Змінні `TARGETOS` та `TARGETARCH` надаються `docker buildx`.

2.  **`final_linux` етап**:
    * Базується на `alpine:3.19`.
    * Копіює скомпільований бінарний файл `kbot` (для Linux) з етапу `builder`.
    * Встановлює `WORKDIR /usr/local/bin/` та `ENTRYPOINT ["./kbot"]`.

3.  **`final_windows` етап**:
    * Базується на `mcr.microsoft.com/windows/nanoserver:ltsc2022`.
    * Копіює скомпільований `kbot.exe` (для Windows) з етапу `builder`.
    * Встановлює `WORKDIR /app/` та `ENTRYPOINT ["./kbot.exe"]`.

4.  **`final` етап (селектор)**:
    * Використовує `FROM final_${TARGETOS}` для автоматичного вибору відповідного фінального образу (Linux або Windows) на основі змінної `TARGETOS`, наданої `docker buildx build --platform ...`.

## 4. Робочі процеси та приклади команд

### Локальна збірка бінарного файлу

Для збірки бінарного файлу для вашої поточної ОС та архітектури (наприклад, `linux/amd64`):
\`\`\`bash
make linux/amd64
\`\`\`

Або використовуйте аліас:
\`\`\`bash
make linux
\`\`\`
Результат буде в `./bin/kbot-linux-amd64`.

### Збірка бінарного файлу та Docker-образу для конкретної платформи

Для збірки бінарного файлу та відповідного Docker-образу (наприклад, для `linux/arm64`):
\`\`\`bash
make WITHDOCKER=true linux/arm64
\`\`\`
Це створить бінарний файл `./bin/kbot-linux-arm64` та Docker-образ з тегом `github.dev/devops101-prom/kbot:<версія>.linux-arm64`.
**Примітка**: Переконайтеся, що файл, на який посилається Makefile (`Dockerfile.mk`), є вашим `Dockerfile.multiarch.runnable`.

### Запуск тестів
\`\`\`bash
make test
\`\`\`

### Очищення артефактів збірки та Docker-образів
Для видалення директорії `./bin`:
\`\`\`bash
make clean
\`\`\`
Для видалення `./bin` та пов'язаних Docker-образів:
\`\`\`bash
make clean IMG-RM=true
\`\`\`

### Збірка багатоархітектурного Docker-образу для публікації

Використовуйте `Dockerfile.multiarch.runnable` та `docker buildx`.

**1. Збірка для однієї платформи (наприклад, `linux/amd64`) та завантаження локально:**
\`\`\`bash
docker buildx build \
  --platform linux/amd64 \
  -t ghcr.io/devops101-prom/kbot:$(git describe --tags --abbrev=0)-$(git rev-parse --short HEAD)-linux-amd64 \
  -f Dockerfile.multiarch.runnable . --load
\`\`\`
*(Замініть `ghcr.io/devops101-prom` на ваш реальний регістр)*

**2. Збірка для кількох платформ та публікація в регістр:**
\`\`\`bash
# Спочатку увійдіть у ваш регістр, наприклад: docker login ghcr.io
VERSION_TAG=$(git describe --tags --abbrev=0)-$(git rev-parse --short HEAD)
IMAGE_NAME="ghcr.io/devops101-prom/kbot" # Замініть на ваш регістр

docker buildx build \
  --platform linux/amd64,linux/arm64,windows/amd64 \
  -t "${IMAGE_NAME}:${VERSION_TAG}" \
  -t "${IMAGE_NAME}:latest" \
  -f Dockerfile.multiarch.runnable . --push
\`\`\`
Ця команда збере багатоплатформний образ та опублікує його з тегами версії та `latest`.

## 5. Важливі примітки

* **Ім'я Dockerfile у Makefile**: У вашому `Makefile` команда для збірки Docker-образу використовує `-f Dockerfile.mk`. Переконайтеся, що файл `Dockerfile.multiarch.runnable` (або той, який ви плануєте використовувати для цього) перейменовано на `Dockerfile.mk` у корені проекту, або оновіть `Makefile` для використання правильного імені файлу.
* **Версіонування Git**: Визначення версії в `Makefile` (`VERSION=$(shell git describe --tags --abbrev=0)-$(shell git rev-parse --short HEAD)`) вимагає наявності Git-тегів та історії комітів. Для коректної роботи всередині Docker-збірки (якщо `Makefile` викликається з Dockerfile, який копіює код), необхідно, щоб директорія `.git` була скопійована в контекст збірки Docker.
* **Ціль `docker-push`**: Як зазначено вище, ціль `docker-push` у `Makefile` потребує доопрацювання для коректної роботи. Рекомендується використовувати `docker push` вручну після збірки образу або інтегрувати з командами `docker buildx build --push`.
* **Невідповідність цілей в Makefile**: Деякі цілі-аліаси (наприклад, `linux-amd64`) посилаються на цілі `build-<os>-<arch>`, які не визначені через `define GO_BUILD_template`. Рекомендується стандартизувати використання цілей формату `<os>/<arch>`.
